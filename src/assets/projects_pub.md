### 문제 해결 과정 1
#### 문제
- OCR 인식 API 처리 시간이 길어 동기 방식 처리 시 요청 지연 및 병목 발생
#### 해결

- 외부 API 제약 환경에서는 응답 속도보다 안정적인 처리 흐름 설계가 더 중요함을 체감
- 비동기 기반 설계가 시스템 확장성과 안정성에 직접적인 영향을 준다는 점을 확인

### 문제 해결 과정 2
#### 문제
- 인식 솔루션 API가 페이지 단위 결과 조회 방식만 제공하며, 전체 문서 데이터를 단일 스레드로 순차 호출하면 전체 페이지 조회 시 응답 지연 및 성능 저하 발생
#### 해결
- ThreadPoolTaskExecutor 를 사용하여 멀티스레드로 다중 페이지 요청
- 모든 페이지 결과를 수신하는 시점에 API 응답
#### 성과
- 멀티스레드 기반 병렬 처리로 전체 문서 조회 시간 단축
- API 응답 지연 해소 및 동시 요청 처리 성능 개선
- 대량 페이지 처리 시에도 안정적인 응답 구조 확보
#### 느낀점
- 외부 API 제약 환경에서는 단순 최적화보다 처리 구조 자체를 개선하는 것이 더 효과적임을 경험
- 순차 처리 구조는 확장성에 한계가 있으며 병렬 처리 기반 설계가 성능에 직접적인 영향을 준다는 점을 체감

### 문제 해결 과정 1
#### 문제
- 다양한 DB 환경(Oracle, MariaDB, MSSQL)을 지원하기 위해 MyBatis 기반 SQL을 DB별로 구현하면서 동일 기능에 대해 DB별로 쿼리를 분리 구현해야 하므로, 중복 SQL 관리 및 유지보수 복잡도가 증가하는 구조가 발생
- 이로 인해 유지보수 비용 상승 및 기능 추가 시 수정 범위가 확대되는 문제 발생
#### 해결
- DB 벤더 종속적인 SQL 구조를 제거하기 위해 데이터 접근 방식을 JPA 기반 ORM 구조로 전환
#### 성과
- DB 벤더 별(MySQL, Oracle, MSSQL)로 분리되어 있던 쿼리를 JPA로 통합하여 코드 중복 제거
- DB 변경 시 별도 쿼리 수정 없이 동작 가능하도록 표준화된 데이터 접근 구조 확보
- 쿼리 관리 포인트 감소로 유지보수 비용 절감 및 개발 생산성 향상
#### 느낀점
- DB 벤더 별로 분기된 SQL을 관리하는 방식은 유지보수 비용을 증가시키고 장애 발생 가능성을 높인다는 것을 체감
- JPA와 같은 ORM을 활용하면 데이터 접근 로직을 추상화하여 환경 변화(DB 변경 등)에 유연하게 대응할 수 있음을 경험
- 향후에는 초기 설계 단계에서부터 특정 DB에 종속되지 않는 구조를 고려하여 표준화된 데이터 접근 방식을 우선 적용하고자 함

### 문제 해결 과정 2
#### 문제
- 사이트 별 버전을 SVN 디렉토리 단위로 분기하여 관리하면서 동일 소스의 중복 관리 및 버전 추적이 어려운 구조 발생
- 이로 인해 코드 변경 이력 관리가 비효율적이고 배포 시 버전 충돌 및 운영 복잡도가 증가하는 문제
#### 해결
- 사이트 별 분기 관리 방식을 제거하고 Git 기반의 브랜치 전략을 도입하여 버전 중심으로 통합 관리
- 단일 코드베이스에서 브랜치 및 태그를 활용해 버전 이력과 배포 관리를 일원화하도록 개선
#### 성과
- 중복 소스 제거 및 단일 저장소 기반으로 형상관리 구조 단순화
- 브랜치/태그 기반 버전 관리로 이력 추적 및 배포 안정성 향상
- 사이트 별 배포 시 충돌 감소 및 운영 효율 개선
#### 느낀점
- 디렉토리 기반 형상관리는 코드 중복과 이력 관리의 한계를 초래한다는 것을 체감
- Git의 브랜치 전략을 활용하면 버전 관리와 협업을 동시에 효율적으로 수행할 수 있음을 경험
- 향후에는 초기 프로젝트 단계부터 형상관리 전략을 구조적으로 설계하는 것이 중요하다고 판단
